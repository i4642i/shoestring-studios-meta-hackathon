# 선정에 유리한 결과물 전략 — Shoestring Studios

작성: 2026-10-27
이 문서는 대회 규정(확인된 사실)을 바탕으로, 어떤 결과물을 만들어야 점수에 유리한지 정리한 것입니다.
- **[규정]** = 공식 자료에서 확인된 사실
- **[판단]** = 규정을 바탕으로 한 추천. 점수를 보장하지 않습니다.

---

## 1. 심사 구조에서 나오는 핵심 결론

| 단계 | [규정] 무엇을 보나 | [판단] 결론 |
|---|---|---|
| 1단계 통과/탈락 | 주제에 맞나, Meta AI 제품을 쓰나 | Meta 모델이 **핵심 기능**이어야 함. 보조로 살짝 쓰는 수준이면 위험 |
| 2단계 채점 | Impact 30%, Meta 도구 25%, 기술 깊이 20%, 시연 25% | 심사위원은 **3분 영상으로 채점**함 → **영상이 가장 중요한 결과물** |
| 3단계 결승 | 트랙별 상위 5팀, 생중계로 데모를 보고 순위 결정 | 결승에 가려면 **실제로 끝까지 도는 것**이 필수 |

[규정] 개인 트랙 심사 초점: **창의성, 기술적 야심, 실제로 돌아가는지**
[판단] 기능을 많이 늘어놓는 것보다 **"교재 한 장 → 완성 영상 + 근거 보고서"가 사람 손 없이 끝까지 도는 것** 하나가 훨씬 유리합니다.

---

## 2. 채점 항목별로 무엇을 만들면 유리한가

### Impact (30%) — 가장 비중이 큼
[규정] 실제로 쓰일 가능성, 누가 혜택을 보나, 주제와 맞나

[판단] 만들 것
- **"누가, 어떤 어려움을, 어떻게 덜어 주나"를 한 문장으로** 정리해서 영상 첫 15초와 README 첫 줄에 넣기
  - 예: "어려운 교재를 혼자 공부하는 사람이, 믿을 수 있는 해설 영상을 몇 분 만에 받는다."
- **실제 교재로 만든 완성 영상 샘플**: 결과물을 직접 보여 주는 것이 가장 강한 증거
- **"믿을 수 있다"는 증거**: 주장↔근거 보고서에서 영상 속 문장을 누르면 원문 구절이 보이는 화면
- (가능하면) **다른 분야 교재로도 한 번 돌린 결과**: "어떤 어려운 글에도 쓸 수 있다"는 주장의 근거

### Use of Meta AI tooling (25%)
[규정] 기본 연동을 넘어선 **창의적 사용**

[판단] 만들 것
- **모델마다 분명한 역할 나누기**: Spark(기획·작가), Wonder(정확성 검사), Image(삽화), Glimmer(반복 검사, 자체 GPU)
  - 모델 하나만 부르는 것보다 "왜 이 일에 이 모델인가"를 설명할 수 있는 구성이 유리함
- **남들이 잘 안 쓸 창의적 활용 1~2개** (아이디어, 만들 수 있을 때만)
  - **Muse Voice Transcribe로 검증**: 완성된 나레이션 음성을 다시 받아쓰기해서 승인된 대본과 비교 → "음성까지 검증된 영상"
  - **SAM 3.1로 교재 그림 잘라내기**: 교재 PDF의 도표나 그림을 분할해서 영상 장면에 그대로 활용
  - **Muse Spark의 멀티모달 입력**: 교재 페이지를 그림째로 읽어 수식과 도표까지 이해
- **공개 모델(Glimmer)을 실제로 돌린 기록**: 보너스 상 후보 조건이기도 함

### Technical depth (20%)
[규정] 탄탄하고 다듬어진, 공들인 엔지니어링

[판단] 만들 것
- **코드로 하는 검증 장치**: "인용문이 원문에 실제로 있는지" 코드가 확인 → AI 말만 믿지 않는 구조
- **에이전트 간 구조화된 주고받기**: JSON 형식, 실패 시 재시도, 검토 불합격 시 다시 쓰기 반복
- **비용과 시간 측정**: 1회 실행에 드는 토큰, 비용, 시간 기록. "Glimmer로 넘겨서 비용이 얼마나 줄었나" 숫자
- **깨끗한 저장소**: README(무엇·왜·어떻게 실행), 설치·실행 스크립트, 작고 자주 한 커밋 기록

### Demo (25%)
[규정] 제대로 돌아가는 시연, 볼 만한 시연 영상. 심사위원은 이 영상으로 채점

[판단] 3분 영상 구성안
| 시간 | 내용 |
|---|---|
| 0:00~0:20 | 문제: 어려운 교재 화면 + "AI 설명은 믿기 어렵다" |
| 0:20~0:40 | 해결책 한 줄 + 결과물 미리보기 (완성 영상 몇 초) |
| 0:40~1:40 | **실제 실행 화면**: 교재를 넣고 → 에이전트들이 일하는 모습(기획, 작가, 검토 불합격 → 다시 쓰기) |
| 1:40~2:30 | 결과: 완성 해설 영상 일부 + 주장↔근거 보고서 클릭 시연 |
| 2:30~3:00 | 어떤 Meta 모델을 어디에 썼나 한 장 정리 + 비용 숫자 + 마무리 |
- 나레이션은 또렷한 영어로 (운영진이 좋은 나레이션을 강조함)
- 대회 중 만든 것만 보여 줄 것 [규정]

## 3. 꼭 피해야 할 것

| [규정] 내용 | [판단] 우리에게 주는 의미 |
|---|---|
| 피해야 할 프로젝트: "교육용 AI 챗봇", "기본 RAG 앱" | **채팅 화면을 중심에 두지 말 것.** 질문-답변이 아니라 "완성 영상을 만드는 제작 파이프라인"으로 보여 줄 것 |
| 피해야 할 프로젝트: Streamlit 앱 | **화면을 Streamlit으로 만들지 말 것** |
| 피해야 할 프로젝트: 대시보드가 핵심 기능인 것 | 에이전트 진행 화면은 **보조 장치**로만. 주인공은 완성 영상과 근거 보고서 |
| 대회 중 만든 것만 시연, 불분명하면 실격 | 기존 코드 재사용 없이 새로 작성. 커밋 기록으로 증명 |
| 권리 없는 데이터·자산 사용은 실격 | **교재 원문을 저장소에 올리지 말 것.** 시연용으로는 저작권 문제가 없는 글(공개 강의 자료, 퍼블릭 도메인, 직접 쓴 글 등)을 쓰는 게 안전. 어떤 자료가 괜찮은지는 출처마다 확인 필요 |
| 저장소는 공개 | 제출 전 시크릿 창에서 확인 |

## 4. 보너스 상과 맞추기

| 보너스 상 | [규정] 조건 | [판단] 우리에게 필요한 것 |
|---|---|---|
| Best Agentic Use-Case (5천) | 자율성, 효과, 실용성 | 사람 개입 없이 끝까지 도는 모습, 검토 불합격 → 스스로 수정하는 장면 |
| Best Creative Build (5천) | Muse Image 또는 Wonder 사용, 독창성 | Wonder 검토 + Image 삽화를 실제로 쓰기 |
| Best Build on Meta Open Weights (1만) | Glimmer 또는 Spark Open을 자체 장비나 파트너에서 실행, 실제 동작 확인 | B200에서 Glimmer를 실제로 돌리고, 그 기록과 설정을 저장소에 남기기 |
| Most Viral (2만) | X 게시물 반응 | 선택. X 계정이 있어야 함 |

[판단] 위 세 상(Agentic, Creative, Open Weights)은 **본 심사를 위한 작업과 겹칩니다.** 따로 일을 늘리지 않아도 후보가 될 수 있는 구조입니다.

## 5. 최종 결과물 목록 (우선순위 순)

| 순위 | 결과물 | 왜 필요한가 |
|---|---|---|
| 1 | **끝까지 도는 파이프라인** (교재 한 장 → 영상 + 보고서) | 1·3단계 통과의 전제, 개인 트랙 "실제로 돌아가는지" |
| 2 | **3분 시연 영상** | 심사위원이 이걸로 채점 (시연 25% + 나머지 항목도 영상으로 판단) |
| 3 | **완성 해설 영상 샘플** (1~2개) | Impact 증거 |
| 4 | **주장↔근거 보고서** (클릭하면 원문 구절이 보이는 웹 페이지) | 차별점, "믿을 수 있다"는 증거 |
| 5 | **공개 GitHub 저장소** (README, 실행 방법, 커밋 기록) | 필수 제출물, 기술 깊이, 새 작업 증명 |
| 6 | **비용·시간 측정 결과** | 기술 깊이, "개인도 쓸 수 있다"는 Impact 근거 |
| 7 | 창의적 Meta 활용 1~2개 (음성 검증, SAM 그림 분할 등) | Meta 도구 점수, Creative 상 |

## 6. 일정 배분 원칙 [판단]

- **1순위를 먼저 끝까지 연결**하고 나서 품질을 올립니다. 각 단계가 거칠어도 일단 처음부터 끝까지 한 번 도는 것을 최대한 빨리 만듭니다.
- **시연 영상 제작에 최소 1~2일**을 남깁니다. 영상이 채점 기준이라 마지막 날 급하게 만들면 손해가 큽니다.
- 창의적 활용(7순위)은 1~6순위가 된 다음에 합니다.
- 마감(한국 11-05 11:00) **하루 전에 제출을 끝내는 것**을 목표로 합니다.

---

## 7. 확인되지 않은 것

- 심사위원이 저장소 코드를 실제로 실행해 보는지
- 결승 생중계에서 참가자가 직접 발표해야 하는지
- 제출 후 마감 전까지 수정할 수 있는지
- 시연에 쓸 교재의 저작권 범위(어디까지 인용 가능한지)
