# Result JSON draft (D8: definition first, code later)

- Status: living design doc (D8). Decided parts are marked
  DECIDED in §12; the v7 target data flow is §15.
- Date: 2026-10-30.
- Implements decisions D1–D9: one result JSON per agent run, split by
  category; lines pick categories; merges go through relay agents;
  video assembly is post-processing; no run-time missing-input requests.

## 1. Shape (one file per agent run)

```json
{
  "producer": "sales_sam",
  "format_version": 1,
  "order_id": "...",
  "run_id": "...",
  "created_at": "2026-10-30T03:00:00",
  "status": "unverified",
  "reviewed_by": null,
  "reviewed_at": null,
  "verified_by": null,
  "verified_at": null,
  "categories": {
    "request": {"version": 1, "data": {}}
  }
}
```

- `producer`: agent id that made this result. No destinations anywhere
  in the file (D1): the agent does not know where results go.
- `format_version`: envelope version, integer, starts at 1. Bump
  only when the header itself changes (producer, ids, status fields).
- `order_id`, `run_id`: the order and the run that produced this.
- `created_at`: local time `YYYY-MM-DDTHH:MM:SS`.
- `status`: `unverified` (just written) → `checked` (payload passed
  its category schema, code check) → `reviewed` (a reviewer agent —
  Vera for storyboard, Iris for narration — compared it with the
  sources via `open_ref` and passed it: every citation passes the
  verbatim check and no open fix remains; otherwise it stays
  `checked` and lists the problems) → `verified` (the developer
  confirmed it in the UI; any category, with or without a reviewer).
- `reviewed_by` / `reviewed_at`: reviewer agent id + time, set when
  the status becomes `reviewed`. `verified_by` / `verified_at`:
  developer id + time, set on confirm.
- A `verified` result is read-only; any change creates a new run
  (new `run_id`), never an edit in place.
- `categories`: `{<name>: {"version": <int>, "data": {...}}}`. Each
  category carries its own version; bump only that category's number
  when its schema changes. The schemas in §§2–4 below describe each
  category's `data`. An agent with one result has one key.
- A receiving agent's check names the category versions it accepts
  (e.g. `request` v1); anything else is refused at the line.

## 2. Sam (`sales_sam`)

Produces `{request, source}`. Consumes the order brief (answers +
attached PDF, via the runner's INPUTS, not lines): Sam starts the
flow. Sam's run: `pc_send_source` (parse + ingest + map + index,
returns the entry ref) → `pc_set_recipients` (who receives this
source) → read → `write_request` (validates `request`, auto-builds
`source` v3 from the sent entry).

`request` payload schema:

```json
{
  "type": "object",
  "required": ["order_id", "client_answers", "source_summary",
               "production_notes", "open_questions"],
  "properties": {
    "order_id": {"type": "string"},
    "client_answers": {
      "type": "object",
      "required": ["audience", "length", "depth", "theme", "source"],
      "properties": {
        "audience": {"type": "string"}, "length": {"type": "string"},
        "depth": {"type": "string"}, "theme": {"type": "string"},
        "source": {"type": "string"}
      }
    },
    "source_summary": {"type": "string"},
    "production_notes": {"type": "array", "items": {"type": "string"}},
    "open_questions": {"type": "array", "items": {"type": "string"}}
  }
}
```

Mirrors today's `request.json` (writer-validated), now retired: agents
write only the result JSON, and the human report is generated by
`render_report` (§11).

## 3. Marty (`pd_marty`)

Produces `{concept, structure}`. Consumes `request` (required)
only: no `source` lines exist anymore — Marty reads the Source
entry through his recipient row (§8.9). The old single
`structure` v1 is split: the idea (`concept` v1) and the skeleton
(`structure` v3, with the time plan). Marty holds a `full` row on
the Source entry, so his prompt carries the full-text chunk
(capped ~100k chars, §8.9); heading/coverage validation checks
the Source entry text.

`concept` v1 payload schema:

```json
{
  "type": "object",
  "required": ["common_theme", "core_question", "viewer_takeaway",
               "intent_overall"],
  "properties": {
    "common_theme": {"type": "string"},
    "core_question": {"type": "string"},
    "viewer_takeaway": {"type": "string"},
    "intent_overall": {"type": "string"}
  }
}
```

- `common_theme`: what the whole source is about. `core_question`:
  the one question the video answers. `viewer_takeaway`: what the
  viewer walks away with. `intent_overall`: why the author built the
  source this way.

`structure` v3 payload schema (static shape; input-relative rules such
as heading coverage and source order stay enforced by the writer tool
at creation time, because pure JSON schema cannot express "heading
exists in the input"):

```json
{
  "type": "object",
  "required": ["source_ref", "parts", "links", "duration"],
  "properties": {
    "source_ref": {"type": "string"},
    "parts": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["id", "heading", "ref", "covers", "keywords"],
        "properties": {
          "id": {"type": "string"}, "heading": {"type": "string"},
          "ref": {"type": "string"}, "covers": {"type": "string"},
          "keywords": {"type": "array", "items": {"type": "string"}}
        }
      }
    },
    "duration": {
      "type": "object",
      "required": ["total_s", "parts"],
      "properties": {
        "total_s": {"type": "integer"},
        "parts": {
          "type": "array",
          "items": {
            "type": "object",
            "required": ["part_id", "seconds", "why"],
            "properties": {
              "part_id": {"type": "string"},
              "seconds": {"type": "integer"},
              "why": {"type": "string"}
            }
          }
        }
      }
    },
    "links": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["from", "to", "why"],
        "properties": {
          "from": {"type": "string"}, "to": {"type": "string"},
          "why": {"type": "string"}
        }
      }
    }
  }
}
```

- `source_ref`: the Source PC entry ref (`pc://source/<id>`).
- Each part's `ref` is its section ref (`pc://source/<id>#s<n>`).
  Non-content sections (exercises, references) are never parts.
- `duration`: Marty's time plan. `total_s` is Marty's seconds
  reading of the request length (`client_answers.length`, e.g.
  "about 10 minutes" → 600); `parts[]` splits it across structure
  parts with a `why` each. Checks: part seconds sum to `total_s`
  (writer tool); `total_s` equals the request length parsed to
  exact seconds (Sam→Marty handoff check).
- Coverage, order, neighbour links, and exact-heading rules are
  unchanged from v1 (writer-enforced).

## 4. Source pointer (RETIRED as a category; recipients deliver it)

The old order pseudo-producer node is RETIRED: no flow node builds
`brief`/`source` anymore. The order brief (answers + attached PDF)
reaches Sam through the runner's INPUTS; Sam sends the PDF to the
Source PC, sets recipients, and writes ONLY `request`. The pointer
lives on the PC entry + `send.json` + the order's `pc_ref`.
`source` v1/v2/v3 and `brief` v1 stay registered only so old runs
still validate, render, and load.

`source` payload schema v3 (small pointer into the Source PC entry;
full text stays in the PC so envelopes never balloon to megabytes):

```json
{
  "type": "object",
  "required": ["ref", "title", "chars", "sections", "recipients"],
  "properties": {
    "ref": {"type": "string"},
    "title": {"type": "string"},
    "chars": {"type": "integer"},
    "sections": {"type": "integer"},
    "recipients": {"type": "array"}
  },
  "additionalProperties": true
}
```

`ref` is the entry address (`pc://source/<id>`, §9).
`recipients` repeats this order's recipient rows
(`[{agent, order_id, kind, parts, set_by, at}]`, §8.9). No flow
line carries `source` anymore: listings deliver it. The v2 transitional
`file`/`head` sidecar is dropped: every agent reads through PC
tools. v1/v2 stay registered so old runs still validate and render.

Entry format:

```json

  "title": "client document title",

  "paragraphs": [{"addr": "s1.1/p3", "text": "..."}],

}
```

- `doc_id`: content hash (§9), so re-parsing the same bytes yields the
  same id and address.
- Paragraphs carry short local addrs; the full stable address is
  `pc://source/<doc_id>#s<section>/p<paragraph>` (§9).

Vision re-reads (worker transcribe stage, map version 2): formulas on
candidate pages and tables under captions are copied from 200 dpi
page renders by the map model (Spark Open), then checked against the
extracted page text before anything is stored.

- `equations`: `[{addr ("eq<section>.<n>"), page, latex, context,
  in (paragraph addrs), transcribed_by, checked, generated_at}]`.
  Accept rule: the context anchors in the page text (full match, or
  a 5+ word clean-prose run in page order; space-insensitive).
  Rejected formulas are not stored; the paragraph keeps its
  candidate tag and its original text is never touched.
- Transcribed tables sit beside their table-image figure as
  `tab<section>.<n>` with `rows`, `markdown`, `transcribed_by`,
  `checked`. Accept rule: every header + cell in page order
  (space-insensitive; bullets `(cid:N)`/`•` ignored; a cell may
  span print lines). Unchecked tables stay stored but are
  navigation only; the image fallback stays.
- Citation rule: crew may cite a formula or table by its address.
  Transcribed LaTeX/cells count as evidence ONLY when `checked`
  is true; `open_ref` blanks unchecked transcriptions and every
  checked read carries "transcribed by model, checked against
  page text".
- Cost guard: candidate pages + captioned table-images only, at
  most 10 vision calls per document, cached by (page, kind,
  prompt version) so rebuilds do not pay again; tokens per call
  in the entry `log.jsonl`.

## 9. Stable reference addresses

Every stored passage gets a stable address:

```text
pc://source/<doc_id>#s<section>/p<paragraph>
pc://theory/<id>#p<paragraph>
pc://article/<id>#p<paragraph>
```

- `<doc_id>` / `<id>`: first 12 hex chars of SHA-256 over the
  normalized content (whitespace-normalized, lowercased). Short to
  write, collision-safe at our scale; re-adding the same document
  gives the same address.
- The model writes only the short ref plus a verbatim quote. The
  system fills in full provenance (url, title, date, fetched_at) from
  the PC entry — the model never copies long URLs by hand.
- A citation in any result JSON:

```json
{"ref": "pc://article/7b2e…#p12", "quote": "<verbatim text>"}
```

- Tool `open_ref(ref)`: returns that passage verbatim with its
  provenance. The caller's PC read grant still applies: no grant, no
  passage.
- Citation check: a citation passes only if `quote` appears verbatim
  in the passage at `ref` (normalize whitespace only). Writer tools
  run this check at write time (same pattern as the existing
  writer-validated outputs); reviewers re-verify through `open_ref`
  and list any failures as problems (the result stays `checked`
  until clean).

## 10. Map builder (per PC, automatic)

The map builder is attached to the PCs, not to agents. Each PC
(Source, Theory, Article) has one ingest pipeline that runs
automatically on every add (`pc_send_source` / `pc_pick_theory` /
`pc_pick_article`):

1. (Theory/Article) fetch the full page text and clean boilerplate
   (§10.1). Source entries arrive parsed, so they skip this step.
2. Content hash → id; if it exists, return the existing ref and stop.
3. Assign paragraph/figure/table/formula addresses (§9).
4. `build_map(entry)` (§10.2).
5. LightRAG indexing for the active embedding profile.

Agents only call add and get the ref back; they never build maps or
indexes. `pc_send_source` waits for the map and the index (bounded;
finished stages are skipped for duplicates) and reports their
status; the entry shows "map: pending" until done. Paragraphs are
readable via `open_ref` right away.

### 10.1 Fetch and clean (Theory/Article)

Search hits are often snippets, not full articles. On add, the PC
fetches the full page text first:

- Tavily Extract endpoint (verified 2026-10-30 from Tavily docs):
  batch up to 20 URLs per request; `basic` costs 1 credit per 5
  successful extractions, `advanced` (adds tables and embedded
  content) 2 per 5; failed extractions cost nothing (the cost basis
  is successful extractions). `chunks_per_source` (1–5, ~800 chars
  each) with `query` bounds `raw_content`; the full content comes
  back when the page fits the chunk budget.
- UNVERIFIED: search-time `raw_content` option and its cost — use
  the Extract endpoint instead.
- Clean: keep only the main article body; drop menus, ads, comments,
  related-link lists, cookie banners.
- If the full text cannot be fetched, store the snippet and mark the
  entry `snippet_only`.

### 10.2 build_map(entry)

1. Code: split sections/subsections (Source: numbered headings;
   Theory/Article: paragraph groups).
2. Code: addresses for every paragraph (`s1.2/p3`) and for figures,
   tables, formulas (`fig1.1`, `tab1.2`, `eq1.3`).
3. Code: detect "omitted" candidates per section — numbers, formulas,
   figure/table mentions, lists, example sentences ("for example",
   "e.g.", "consider") — each with its exact ref.
4. Code: extract key terms (capitalized, quoted, bold), original
   wording.
5. LLM, one call per section: given the section text with paragraph
   numbers, return only JSON `{summary: [{text, see: "p1-p3"}]}`.
6. Code check: every "see" range exists; every omitted candidate not
   covered by the summary goes into "omitted" as `{what, see}`. On
   failure retry that section once, then mark "summary_missing"
   (never invent).
7. LLM, one call: entry summary (3–5 sentences) from section
   summaries.

### 10.3 Map shape (per section)

```json
{"ref": "…", "heading": "…",
 "summary": [{"text": "…", "see": "p1-p3"}],
 "omitted": [{"what": "…", "see": "p4"}],
 "key_terms": ["…"], "has": ["fig1.1", "tab1.2"],
 "chars": 1234, "subsections": ["…"]}
```

- Summaries are navigation only, never evidence: the writer tool
  rejects quotes taken from a summary.
- When the writer tool rejects a claim without evidence, it suggests
  a matching "omitted" ref from the map.

### 10.4 Logging

Per entry: map/index time, LLM calls, tokens.

### 10.5 Where PC data and maps live

```text
storage/_pc/<pc>/entries/<id>/entry.json   full text, addresses, provenance
storage/_pc/<pc>/entries/<id>/map.json     build_map result
storage/_pc/<pc>/entries/<id>/figures/     images (Source PC)
storage/_pc/<pc>/index/<profile>/          LightRAG index per profile
```

`<pc>` = source | theory | article; `<id>` = content-hash id from
the ref.

- The map does not depend on the embedding profile, so it lives
  outside `index/` and is reused when the profile changes.
- `map.json` header: `built_at`, `llm_model`, `map_version`, `status`
  (`pending` | `partial` | `done`). Rebuild only when `map_version`
  or `llm_model` changes.
- `storage/_pc/` is gitignored as a whole (PC data is never
  committed).

## 13. Stage-2 research rules (Cleo/Rex)

```text
Source PC ..(map + refs)..> Cleo, Rex
Marty --(concept, structure)--> Cleo, Rex
Cleo <-> Theory PC   Rex <-> Article PC
Cleo -> "concepts": easy theory explanation report (§5.1)
Rex  -> "cases": case research report (§5.2)
```

Both follow Marty's concept and structure, part by part.

### 13.1 Key rule: search wide, store only picks

- Search hits are NOT stored in the PCs. Hits live only in the run
  log as `{query, title, url, snippet}` per search, so reviewers see
  what was considered.
- Cleo/Rex PICK only items they judge useful:

```text
pc_pick_theory(url, part_id, why_important, how_to_use) -> ref
pc_pick_article(url, part_id, why_important, how_to_use) -> ref
```

- A pick runs the full PC ingest on the URL: fetch full text,
  clean (§10.1), content-hash id (§9; same content = same ref,
  no-op), paragraph addresses, `build_map` (§10.2), LightRAG
  indexing (§8.4). It returns the entry ref.
- Every pick records `{picked_by, order_id, run_id, part_id,
  reason}` in the run log (`research.jsonl`, §13.3). The PC entry
  itself keeps only `added_by` (first adder): pick records live
  with the run, because one entry can be picked by many orders.
- Pick only what will be cited or must be read by later agents.
  This is written in Cleo/Rex instructions; there is no hard
  count limit.
- Reports render picks as clickable refs (`open_ref`).

### 13.2 Handoff to later agents (Ash and after)

- Like the Source PC handoff, later agents get access ONLY to the
  items picked for their order — never the whole PC. Per pick:
  the entry map, its refs, and Cleo/Rex's `why_important` +
  `how_to_use` from the report's `picks[]`.
- The order's pick set is the union of `picks[].ref` across the
  `concepts` and `cases` results for that order. No new store:
  the reports ARE the pick set.
- Read scope is enforced, not advisory: on Theory/Article PCs
  the recipients list IS the pick scope (§8.9) — readers other
  than the picker open only refs inside their listed parts.
  Anything else is refused with "no access to this item".
- "Preview start prompt" for a later agent shows only the picks
  (map + refs + reasons), never full PC dumps. The preview uses the
  same recipients-gated builder as real runs (§8.9); non-listed
  entries are refused, not shown.

### 13.3 Run log (`research.jsonl`)

One line per event, under the agent's run dir:

```jsonl
{"ev": "search", "query": "…", "tool": "pc_search_theory",
 "hits": [{"title": "…", "url": "…", "snippet": "…"}]}
{"ev": "pick", "ref": "pc://theory/…", "url": "…",
 "part_id": "p2", "picked_by": "explain_cleo",
 "order_id": "…", "run_id": "…", "reason": "…"}
```

- Status line per run: searches run, hits seen, picks made,
  citations written. Retrieval behavior per task: a need-list
  checklist, short search hits, the status line, and these logs.

### 13.4 Writer checks (Cleo/Rex)

At write time, the writer tool verifies, in order:

1. Schema check: payload matches `concepts` v1 / `cases` v1.
2. Verbatim citation check: every `claims[].citations[]` and every
   pick `evidence` passes the §9 check (quote appears verbatim at
   `ref`, whitespace only normalized). Summary/map text is never
   quotable evidence.
3. "No evidence, no save": every claim carries ≥1 citation; every
   case carries ≥1 claim with ≥1 citation. On failure the tool
   refuses and suggests a matching ref (map's omitted list).
4. Picks/report match: the set of pick refs in the report equals
   the set of items picked in this run (from `research.jsonl`) —
   no unexplained pick, no unpicked ref.

### 13.5 Role quality bars

- Cleo's "easy" test (§8.8): a curious adult can follow it; jargon
  is explained on the spot; an analogy or concrete example is
  present; the core idea works without formulas.
- Rex: real cases only, each with a date and cited sources. No
  invented companies, events, or quotes.
