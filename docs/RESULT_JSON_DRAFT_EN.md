# Result JSON draft (D8: definition first, code later)

- Status: DRAFT for decision. No code implements this yet.
- Date: 2026-10-30.
- Implements decisions D1–D9: one result JSON per agent run, split by
  category; lines pick categories; merges go through relay agents;
  video assembly is post-processing; no run-time missing-input requests.

## 1. Shape (one file per agent run)

```json
{
  "producer": "sales_sam",
  "format_version": 1,
  "order_id": "...",
  "run_id": "...",
  "created_at": "2026-10-30T03:00:00",
  "status": "unverified",
  "reviewed_by": null,
  "reviewed_at": null,
  "verified_by": null,
  "verified_at": null,
  "categories": {
    "request": {"version": 1, "data": {}}
  }
}
```

- `producer`: agent id that made this result. No destinations anywhere
  in the file (D1): the agent does not know where results go.
- `format_version`: envelope version, integer, starts at 1. Bump
  only when the header itself changes (producer, ids, status fields).
- `order_id`, `run_id`: the order and the run that produced this.
- `created_at`: local time `YYYY-MM-DDTHH:MM:SS`.
- `status`: `unverified` (just written) → `checked` (payload passed
  its category schema, code check) → `reviewed` (a reviewer agent —
  Vera for storyboard, Iris for narration — compared it with the
  sources via `open_ref` and passed it: every citation passes the
  verbatim check and no open fix remains; otherwise it stays
  `checked` and lists the problems) → `verified` (the developer
  confirmed it in the UI; any category, with or without a reviewer).
- `reviewed_by` / `reviewed_at`: reviewer agent id + time, set when
  the status becomes `reviewed`. `verified_by` / `verified_at`:
  developer id + time, set on confirm.
- A `verified` result is read-only; any change creates a new run
  (new `run_id`), never an edit in place.
- `categories`: `{<name>: {"version": <int>, "data": {...}}}`. Each
  category carries its own version; bump only that category's number
  when its schema changes. The schemas in §§2–4 below describe each
  category's `data`. An agent with one result has one key.
- A receiving agent's check names the category versions it accepts
  (e.g. `request` v1); anything else is refused at the line.

## 4. Order pseudo-producer (line inputs need schemas too)

`Order` is not an agent run, but its two categories ride lines, so they
are defined here with the same schema language.

`brief` payload schema:

```json
{
  "type": "object",
  "required": ["order_id", "answers", "source_file"],
  "properties": {
    "order_id": {"type": "string"},
    "answers": {
      "type": "object",
      "required": ["audience", "length", "depth", "theme"],
      "properties": {
        "audience": {"type": "string"}, "length": {"type": "string"},
        "depth": {"type": "string"}, "theme": {"type": "string"}
      },
      "additionalProperties": true
    },
    "source_file": {"type": "string"}
  },
  "additionalProperties": true
}
```

`source` payload schema v2 (small pointer into the Source PC entry;
full text stays in the PC so envelopes never balloon to megabytes):

```json
{
  "type": "object",
  "required": ["ref", "title", "chars", "sections"],
  "properties": {
    "ref": {"type": "string"},
    "title": {"type": "string"},
    "chars": {"type": "integer"},
    "sections": {"type": "integer"},
    "file": {"type": "string"},
    "head": {"type": "string"}
  },
  "additionalProperties": true
}
```

`ref` is the entry address (`pc://source/<id>`, §9). `file`/`head`
are transitional: the order node still ships the sidecar markdown
until agents read via PC tools, then they drop out.

## 5. Crew plan (stages 0–7): who makes and takes what

One result JSON per agent run (§1). Each role below lists the
categories it produces and the categories it receives. Receives are
delivered by flow lines (D1: no destinations in any JSON); a role may
take inputs from several senders (D4). Reviewers write a new
`*_checked` category instead of overwriting, so no two senders ever
emit the same category into one agent (see Q4). Full JSON schemas for
the new categories follow once the category set is approved.

| Stage | Role | Receives | Produces |
|---|---|---|---|
| 0 | Sales (Sam) | `brief`, `source` | `request` (§2) |
| 1 | Structure writer (Marty) | `request`, `source` | `structure` (§3) |
| 2 | Concept explainer | `structure`, `source` | `concepts` |
| 2 | Case researcher | `structure`, `source` | `cases` |
| 3 | Planning PD | `request`, `structure`, `concepts`, `cases` | `plan` |
| 4 | Storyboard writer | `plan`, `structure` | `storyboard` |
| 5 | Storyboard reviewer | `storyboard`, `source` | `storyboard_checked` |
| 6 | Narration writer | `storyboard_checked`, `plan` | `narration` |
| 7 | Narration reviewer | `narration`, `source` | `narration_checked` |

New category payloads (field sketches, schemas later):

- `concepts`: per part `{part_id, what, origin, simple_take,
  sources: [{title, url_or_ref, cited_for}]}` — what the concept is,
  why it came about, how to explain it simply.
- `cases`: `{part_id, cases: [{title, kind (event/company/person/
  film), summary, fit_why, sources: [...]}]}` — real cases viewers
  relate to, attached to parts.
- `plan`: `{audience, message, angle, fun_hooks[], flow: {intro,
  body[], conclusion}, page_budget}` — for whom, what, from which
  angle, how to make it fun; intro → body → conclusion.
- `storyboard`: `{pages: [{n, learn, screen, material, next_link}]}` —
  what the viewer learns, the screen, source/material used, link to
  the next page.
- `storyboard_checked`: `{pages: [...same shape, corrected...],
  fixes: [{page, was, now, why}]}` — facts fixed against source and
  materials.
- `narration`: `{pages: [{n, section (intro/body/outro), lines[],
  evidence: [{fact, source_ref}]}]}` — lines per page with evidence
  for each fact and number.
- `narration_checked`: `{pages: [...same shape, corrected...],
  fixes: [{page, was, now, why}]}` — lines fixed against source and
  materials.

## 6. Rules this draft follows (from D1–D9)

- No destinations in any JSON (D1). No per-category files (D2): one
  JSON per run, categories inside.
- Lines filter categories; several senders may feed one agent (D3–D4).
  Same category from two senders has no fixed rule: direct receive or
  relay-agent merge is decided per flow (D7 principle). Every received
  category keeps its sender label (Q4).
- Merging is a relay agent's instructions, never a code block (D5).
- Scene/video assembly is a post-processing page, not an agent (D6).
  It still writes a result JSON as producer `postprocess` (Q5).
- Every needed input must arrive by design; no run-time requests (D7).

## 8. Company computers (shared stores, not agents)

Three shared stores. They are not agents: they hold no opinions, run
no steps, and write no result JSON. Agents reach them only through
tools listed in their own `agent.json` — tools are the only permission
mechanism. External materials are split by purpose: Theory (explain)
vs Article (cases).

### 8.1 Source PC

Parsed results of the client's documents: markdown, images, section
list. Section list: all crew. Full text: Marty, Cleo, Rex (see §8.6).
Write: intake only (Sam's parser step).

Entry format:

```json
{
  "doc_id": "a3f9c1d4e2b8",
  "title": "client document title",
  "origin_file": "upload original name.pdf",
  "order_id": "...",
  "parsed_at": "2026-10-30T03:00:00",
  "added_by": "sales_sam",
  "sections": [{"n": "1.1", "heading": "..."}],
  "paragraphs": [{"addr": "s1.1/p3", "text": "..."}],
  "images": [{"file": "...", "caption": "..."}]
}
```

- `doc_id`: content hash (§9), so re-parsing the same bytes yields the
  same id and address.
- Paragraphs carry short local addrs; the full stable address is
  `pc://source/<doc_id>#s<section>/p<paragraph>` (§9).
- Provenance on every entry: origin file, order, parse time, adder.

### 8.2 Theory PC

Concept explanations, lectures, papers, technical articles. Search +
add: Cleo (concept explainer) only. Full address:
`pc://theory/<id>#p<paragraph>`.

Entry format (shared with the Article PC):

```json
{
  "theory_id": "7b2e…",
  "url": "https://…",
  "title": "…",
  "publisher": "…",
  "date": "2026-01-15",
  "fetched_at": "2026-10-30T03:00:00",
  "added_by": "explain_cleo",
  "text": "full text (see Q9)",
  "paragraphs": [{"addr": "p12", "text": "..."}]
}
```

- `theory_id`: content hash (§9).
- Provenance on every entry: url, title, publisher, date, fetch time,
  adder. The model never copies these by hand (§9).

### 8.3 Article PC

Real events, companies, people, films used as cases. Search + add:
Rex (case researcher) only. Full address:
`pc://article/<id>#p<paragraph>`. Same entry format, duplicate
rules, indexing, and ref rules as the Theory PC (§§8.4–8.6, §9);
only the contents differ.

### 8.4 Indexing

LightRAG, one index per PC per embedding profile, reusing the agent
profile scheme (`local`, `jetson`): `storage/_pc/<pc>/index/<profile>/`
(see §10.5). Same rules as agent indexes: one model+dim per index,
cross-model queries refused, per-profile markers.

### 8.5 Duplicates

- Same content added twice → same id → add is a no-op returning the
  existing address. No duplicate entry is ever stored.
- Same url, changed content on re-fetch → a NEW entry (new id); the
  old entry is kept, so existing refs never rot. The entry notes
  `supersedes: <old_id>` (informational only).

## 9. Stable reference addresses

Every stored passage gets a stable address:

```text
pc://source/<doc_id>#s<section>/p<paragraph>
pc://theory/<id>#p<paragraph>
pc://article/<id>#p<paragraph>
```

- `<doc_id>` / `<id>`: first 12 hex chars of SHA-256 over the
  normalized content (whitespace-normalized, lowercased). Short to
  write, collision-safe at our scale; re-adding the same document
  gives the same address.
- The model writes only the short ref plus a verbatim quote. The
  system fills in full provenance (url, title, date, fetched_at) from
  the PC entry — the model never copies long URLs by hand.
- A citation in any result JSON:

```json
{"ref": "pc://article/7b2e…#p12", "quote": "<verbatim text>"}
```

- Tool `open_ref(ref)`: returns that passage verbatim with its
  provenance. The caller's PC read grant still applies: no grant, no
  passage.
- Citation check: a citation passes only if `quote` appears verbatim
  in the passage at `ref` (normalize whitespace only). Writer tools
  run this check at write time (same pattern as the existing
  writer-validated outputs); reviewers re-verify through `open_ref`
  and list any failures as problems (the result stays `checked`
  until clean).

## 10. Map builder (per PC, automatic)

The map builder is attached to the PCs, not to agents. Each PC
(Source, Theory, Article) has one ingest pipeline that runs
automatically on every add (`pc_add_source` / `pc_add_theory` /
`pc_add_article`):

1. (Theory/Article) fetch the full page text and clean boilerplate
   (§10.1). Source entries arrive parsed, so they skip this step.
2. Content hash → id; if it exists, return the existing ref and stop.
3. Assign paragraph/figure/table/formula addresses (§9).
4. `build_map(entry)` (§10.2).
5. LightRAG indexing for the active embedding profile.

Agents only call add and get the ref back; they never build maps or
indexes. The add returns the ref immediately; steps 4–5 run in the
background and the entry shows "map: pending" until done. Paragraphs
are readable via `open_ref` right away.

### 10.1 Fetch and clean (Theory/Article)

Search hits are often snippets, not full articles. On add, the PC
fetches the full page text first:

- Tavily Extract endpoint (verified 2026-10-30 from Tavily docs):
  batch up to 20 URLs per request; `basic` costs 1 credit per 5
  successful extractions, `advanced` (adds tables and embedded
  content) 2 per 5; failed extractions cost nothing (the cost basis
  is successful extractions). `chunks_per_source` (1–5, ~800 chars
  each) with `query` bounds `raw_content`; the full content comes
  back when the page fits the chunk budget.
- UNVERIFIED: search-time `raw_content` option and its cost — use
  the Extract endpoint instead.
- Clean: keep only the main article body; drop menus, ads, comments,
  related-link lists, cookie banners.
- If the full text cannot be fetched, store the snippet and mark the
  entry `snippet_only`.

### 10.2 build_map(entry)

1. Code: split sections/subsections (Source: numbered headings;
   Theory/Article: paragraph groups).
2. Code: addresses for every paragraph (`s1.2/p3`) and for figures,
   tables, formulas (`fig1.1`, `tab1.2`, `eq1.3`).
3. Code: detect "omitted" candidates per section — numbers, formulas,
   figure/table mentions, lists, example sentences ("for example",
   "e.g.", "consider") — each with its exact ref.
4. Code: extract key terms (capitalized, quoted, bold), original
   wording.
5. LLM, one call per section: given the section text with paragraph
   numbers, return only JSON `{summary: [{text, see: "p1-p3"}]}`.
6. Code check: every "see" range exists; every omitted candidate not
   covered by the summary goes into "omitted" as `{what, see}`. On
   failure retry that section once, then mark "summary_missing"
   (never invent).
7. LLM, one call: entry summary (3–5 sentences) from section
   summaries.

### 10.3 Map shape (per section)

```json
{"ref": "…", "heading": "…",
 "summary": [{"text": "…", "see": "p1-p3"}],
 "omitted": [{"what": "…", "see": "p4"}],
 "key_terms": ["…"], "has": ["fig1.1", "tab1.2"],
 "chars": 1234, "subsections": ["…"]}
```

- Summaries are navigation only, never evidence: the writer tool
  rejects quotes taken from a summary.
- When the writer tool rejects a claim without evidence, it suggests
  a matching "omitted" ref from the map.

### 10.4 Logging

Per entry: map/index time, LLM calls, tokens.

### 10.5 Where PC data and maps live

```text
storage/_pc/<pc>/entries/<id>/entry.json   full text, addresses, provenance
storage/_pc/<pc>/entries/<id>/map.json     build_map result
storage/_pc/<pc>/entries/<id>/figures/     images (Source PC)
storage/_pc/<pc>/index/<profile>/          LightRAG index per profile
```

`<pc>` = source | theory | article; `<id>` = content-hash id from
the ref.

- The map does not depend on the embedding profile, so it lives
  outside `index/` and is reused when the profile changes.
- `map.json` header: `built_at`, `llm_model`, `map_version`, `status`
  (`pending` | `partial` | `done`). Rebuild only when `map_version`
  or `llm_model` changes.
- `storage/_pc/` is gitignored as a whole (PC data is never
  committed).

## 11. Cutover and render_report (Q6)

- Agents write ONLY the result JSON. It is the single source of
  truth. Standalone `request.json` / `structure.json` are retired:
  writers stop emitting them and every reader switches to the
  envelope.
- The platform has `render_report(result)`: one report template per
  category (and category version). It turns any result JSON into a
  human-readable report (.md and a page in the UI), automatically,
  after each run.
- Citations `{ref, quote}` render as links that open the passage via
  `open_ref`.
- Reports are marked "generated from \<run_id\>, do not edit" and are
  never read by agents or checks.
- Anything a human must read (reasons, notes) must exist as a field
  in the category schema; the report shows nothing that is not in
  the JSON.

Code places that read the old files (Sam/Marty switch list):

- Writers: `agents/_frame/tools.py` — `write_structure` writes
  `run_dir/structure.json`, `write_request` writes
  `run_dir/request.json` + `request.md`, `OUTPUTS` maps each writer
  to its file.
- Schemas: `agents/_frame/schemas.py` — `validate_structure`,
  `validate_request`, `render_request_md` (the first
  `render_report` template is born here).
- Server: `scripts/server.py` — `io.output` follows `OUTPUTS` on
  tool change; add-employee scaffold defaults to
  `structure.json`; order startproduction copies
  `run_dir/{request.md, request.json}` into `orders/<id>/` and reads
  `orders/<id>/request.md` back as `request_md`.
- UI: `index.html` — order result renders `r.request_md`.
- Agents: `agents/sales_sam/agent.json` (`io.output: request.md`,
  done lines), `agents/pd_marty/agent.json`
  (`io.output: structure.json`); new agents' `io.inputs` naming
  `structure.json` / `request.json` (`explain_cleo`, `case_rex`,
  `board_penn`, `plan_ash`) re-point at envelope categories.
- Tests: `scripts/smoke_server.py` — "detail has io" expects
  `structure.json`, "io follows writer" expects `draft.json`.
- Docs follow: `AGENT_STANDARD_EN.md` §3, `ADD_EMPLOYEE_EN.md`
  scaffold/output rules.
